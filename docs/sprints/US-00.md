# US-00: Fundação do BUILT-RAG-V1 (Camada 0)

> A US-00 é uma sprint: tem várias etapas, executadas uma por vez. Este arquivo é o prompt para o agente e também o registro das etapas.

## 1. Como usar este arquivo

**Agente:**

- Leia, nesta ordem: `AGENTS.md`, `docs/glossary.md`, `docs/adr/0001-ddd.md`, `docs/adr/0002-v1-scope.md`, `docs/adr/0003-v1-architecture.md` e este arquivo.
- Execute **uma etapa por vez**. Ao terminar: escreva o resumo (formato na seção 9) e **pare**. Só siga quando o dono disser "próxima".
- Se este arquivo e o `AGENTS.md` divergirem, vale o `AGENTS.md`. Avise no resumo.
- Em dúvida, pare e pergunte.

## 2. Objetivo

Montar a fundação do projeto: pastas, ferramentas de qualidade e testes de arquitetura que barram violações das regras. Assim, todo código das camadas seguintes nasce dentro das regras.

**Nenhuma regra de negócio é escrita nesta sprint.**

## 3. Contexto

- **A BUILT** é um serviço de entrega sob demanda, com precificação personalizada e também valores fixos, e usa assistentes de IA para atender e entregar o serviço ao cliente de forma automatizada e quase autônoma (desenvolvedores intervêm por pedido de stakeholders ou por mudanças de negócio). Os assistentes respondem a partir de uma base de conhecimento (a vault, no Obsidian) usando RAG. Existem três LLMs, uma para leads, uma para clientes e uma para a operação interna.
- **A V1** é o chatbot público de topo de funil (LLM 1). Ele fica exposto na web, então segurança é prioridade.
- **Stack:** Python 3.12, `uv`, layout `src`, pacote `built`.
- **Arquitetura da V1** (ADR-0001, ADR-0002 e ADR-0003): `policy` com três andares (`domain`, `application`, `infrastructure`) e um pacote `published`; `knowledge` em módulos planos; o pacote `infrastructure` com o motor `rag` e os adaptadores; `shared_kernel` puro; `entrypoints/` existe desde já, mas o código dela nasce na Camada 4. A árvore completa está na Etapa 2.
- **Atenção:** os andares existem só dentro do `policy`. Nunca ficam soltos na raiz de `src/built/`. O nome `infrastructure` aparece duas vezes: o andar `policy/infrastructure` e o pacote `infrastructure/` da raiz.
- **Porta pública do `policy`:** `built.policy.published` e `built.policy.application`.

## 4. Escopo

**Entra:** pastas e módulos com docstrings, configuração das ferramentas, testes de arquitetura e documentos de apoio.

**Não entra (proibido nesta sprint):**

- Qualquer classe ou função de negócio.
- Qdrant, SDK de LLM, FastAPI, Pydantic, OpenTelemetry, Phoenix, Hypothesis.
- Código dentro de `entrypoints/` (a pasta entra só com docstring; o código nasce na Camada 4).
- Alterar o conteúdo de `AGENTS.md`, do glossary ou dos ADRs.
- CI, CODEOWNERS, template de PR e proteção de branch (Etapas 5 e 6, adiadas).
- Qualquer teste além dos casos da Etapa 4 (regra 19 do `AGENTS.md`).
- Limites de cobertura de testes e qualquer configuração fora desta lista.

**Dependências permitidas** (todas só de desenvolvimento): `ruff`, `mypy`, `pytest`, `pytest-cov`, `import-linter`, `pre-commit`. Nenhuma dependência de execução. Qualquer outra precisa de aprovação antes.


Docstrings:

- `shared_kernel`: peças comuns mínimas. Só biblioteca padrão. Não importa nenhum contexto.
- `policy/published`: vocabulário público do `policy`. Outros contextos importam daqui.
- `policy/domain`: regras puras de acesso. Só biblioteca padrão.
- `policy/application`: casos de uso e portas do `policy`. É a porta pública, junto com `published`.
- `policy/infrastructure`: tecnologia do `policy` (validação de token, sessão). Em espera na V1.
- `knowledge/model`: o que é um documento válido (contrato Built Knowledge Model).
- `knowledge/ingestion`: lê a vault, valida, divide em chunks e indexa. É o único que escreve no índice.
- `infrastructure`: o motor de resposta e os adaptadores do mundo externo. Não é o andar `infrastructure` do `policy`.
- `infrastructure/rag/ports.py`: interfaces que o motor conhece (LLM, telemetria, busca no índice).
- `infrastructure/rag/retriever.py`: faz a busca, sempre com o filtro do `policy`.
- `infrastructure/rag/gate.py`: confere os chunks antes de irem para a LLM. Falha fechado.
- `infrastructure/rag/prompt.py`: montagem do prompt e limite de janela.
- `infrastructure/rag/output_linter.py`: confere a resposta da LLM depois de gerada.
- `infrastructure/rag/pipeline.py`: orquestra o fluxo da V1.
- `infrastructure/adapters`: contratos com o mundo externo. O motor `rag` nunca os importa.
- `infrastructure/adapters/qdrant`: o único lugar que fala com o Qdrant.
- `infrastructure/adapters/llm`: provedor de LLM.
- `infrastructure/adapters/telemetry`: OpenTelemetry e Phoenix.
- `entrypoints`: a API. Monta as peças e chama o pipeline. O código chega na Camada 4.

### Etapa 4: Testes de arquitetura

**Regras a impor** (ADR-0003, seção 3)

| #   | Regra                                                                                                                                                                     |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | No `policy`: `infrastructure` → `application` → `domain`. Nunca no sentido contrário.                                                                                     |
| R2  | `policy/domain` só importa a biblioteca padrão (`sys.stdlib_module_names`), `built.shared_kernel`, ele mesmo e `built.policy.published`.                                  |
| R3  | `shared_kernel` só importa a biblioteca padrão e a si mesmo. Nenhum contexto, nenhuma biblioteca externa.                                                                 |
| R4  | Fora do `policy`, tudo (`knowledge`, `infrastructure`, `entrypoints`) só usa do `policy`: `built.policy.published` e `built.policy.application`.                          |
| R5  | `built.infrastructure.adapters.qdrant` só é importado por `built.knowledge.ingestion`, por `built.entrypoints` e por ele mesmo.                                          |
| R6  | `built.infrastructure.rag` nunca importa `built.infrastructure.adapters`. Os adaptadores `llm` e `telemetry` só são importados por `built.entrypoints` e por eles mesmos. |

**Como implementar**

- R1, R4, R5 e R6: `import-linter`, configurado no `pyproject.toml`.
- R2 e R3: teste em `pytest` que analisa os imports com `ast`, por **lista permitida** (não proibida), para funcionar mesmo com pacotes ainda não instalados. Trate imports relativos.
- Se o `import-linter` não conseguir expressar uma regra, implemente-a como teste em `tests/architecture/` e explique no resumo.
